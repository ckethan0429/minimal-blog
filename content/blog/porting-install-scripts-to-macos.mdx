리눅스에서 잘 돌던 설치 스크립트를 macOS로 가져오면, `#!/usr/bin/env bash` 한 줄이 같다고 해서 그대로 동작하지 않는다. 커널도 다르고, 서비스 매니저도 다르고, 기본으로 깔린 유틸리티조차 다르다. 최근에 한 리눅스용 인스톨러를 macOS로 이식하면서 반복적으로 부딪힌 세 가지 차이를 정리해 둔다.

## 1. 서비스 자동화: systemd → launchd

리눅스 인스톨러가 가장 흔히 기대는 게 **systemd**다. "설정 파일이 바뀌면 서비스를 다시 시작하기 전에 훅을 하나 끼워라" 같은 요구를 systemd에서는 드롭인(drop-in)으로 처리한다.

```ini
# ~/.config/systemd/user/myservice.service.d/hook.conf
[Service]
ExecStartPre=-/path/to/venv/bin/python /path/to/reapply.py
```

macOS에는 systemd가 없다. 대신 **launchd**가 그 역할을 한다. 그런데 launchd에는 `ExecStartPre`에 정확히 대응하는 개념이 없다. 대신 접근 방식을 바꾸면 오히려 더 깔끔하게 풀린다. **파일이 바뀔 때 반응하는 에이전트**를 하나 두는 것이다. `WatchPaths`가 그 역할을 한다.

```xml
<!-- ~/Library/LaunchAgents/com.example.reapply.plist -->
<?xml version="1.0" encoding="UTF-8"?>
<!DOCTYPE plist PUBLIC "-//Apple//DTD PLIST 1.0//EN"
  "http://www.apple.com/DTDs/PropertyList-1.0.dtd">
<plist version="1.0">
<dict>
  <key>Label</key>            <string>com.example.reapply</string>
  <key>ProgramArguments</key>
  <array>
    <string>/path/to/venv/bin/python</string>
    <string>/path/to/reapply.py</string>
  </array>
  <key>WatchPaths</key>
  <array>
    <string>/path/to/target-file</string>
  </array>
  <key>RunAtLoad</key>        <true/>
</dict>
</plist>
```

`RunAtLoad`로 로그인/로드 시 한 번 실행하고, `WatchPaths`로 대상 파일이 갱신될 때마다 다시 실행한다. 로딩은 이렇게 한다.

```bash
launchctl unload "$PLIST" 2>/dev/null || true
launchctl load -w "$PLIST"
```

한 가지 주의할 점: `WatchPaths`가 감시하는 파일을 에이전트 자신이 수정하면 다시 트리거된다. 그래서 재적용 스크립트는 반드시 **멱등(idempotent)** 해야 한다. 이미 처리된 상태면 파일을 건드리지 않고 조용히 끝내야 무한 루프에 빠지지 않는다.

## 2. `timeout`이 없다

리눅스 스크립트에서 흔히 쓰는 `timeout 30 some-command`는 macOS에서 바로 막힌다. 기본 설치에 `timeout`이 없기 때문이다. GNU coreutils를 Homebrew로 설치하면 `gtimeout`이라는 이름으로 들어온다.

의존성을 강제하고 싶지 않다면, 있으면 그대로 쓰고 없으면 셸만으로 흉내 내는 헬퍼를 두는 편이 이식성이 좋다.

```bash
run_timeout() { # run_timeout SECONDS cmd...
  local secs="$1"; shift
  if command -v gtimeout >/dev/null 2>&1; then gtimeout "$secs" "$@"; return $?; fi
  if command -v timeout  >/dev/null 2>&1; then timeout  "$secs" "$@"; return $?; fi
  # 폴백: 백그라운드로 띄우고 제한 시간 뒤에 정리
  "$@" & local pid=$!
  ( sleep "$secs"; kill -TERM "$pid" 2>/dev/null
    sleep 2;       kill -KILL "$pid" 2>/dev/null ) >/dev/null 2>&1 &
  local watcher=$!
  wait "$pid" 2>/dev/null; local rc=$?
  kill "$watcher" 2>/dev/null || true
  return $rc
}
```

이렇게 해두면 coreutils가 설치돼 있든 아니든 `run_timeout 30 some-command`가 그대로 동작한다.

## 3. 자격 증명은 파일이 아니라 Keychain에 있을 수 있다

리눅스 프로그램은 토큰이나 자격 증명을 보통 `~/.config/...` 아래 평범한 파일로 둔다. 그래서 인스톨러가 프리플라이트에서 이렇게 확인한다.

```bash
[ -f "$HOME/.some-tool/credentials.json" ] || { echo "로그인이 필요합니다"; exit 1; }
```

같은 도구라도 macOS 빌드는 자격 증명을 **Keychain**에 넣는 경우가 많다. 이 경우 위 파일 검사는 실제로 로그인이 되어 있어도 무조건 실패한다. Keychain은 파일 시스템에 그런 경로로 존재하지 않기 때문이다.

macOS에서는 `security` 커맨드로 확인한다.

```bash
security find-generic-password -s "Some Tool-credentials" >/dev/null 2>&1 \
  && echo "keychain 자격 증명 있음"
```

이식할 때는 프리플라이트를 "파일 **또는** Keychain 중 하나면 통과"로 완화하는 게 안전하다.

```bash
if [ -f "$HOME/.some-tool/credentials.json" ] \
   || security find-generic-password -s "Some Tool-credentials" >/dev/null 2>&1; then
  : # OK
else
  echo "로그인이 필요합니다"; exit 1
fi
```

## 보너스: BSD vs GNU 유틸리티

macOS의 기본 커맨드라인 도구는 GNU가 아니라 **BSD** 계열이다. 자주 걸리는 차이는 다음과 같다.

| 작업 | GNU (리눅스) | BSD (macOS) |
| --- | --- | --- |
| 제자리 편집 | `sed -i 's/a/b/' f` | `sed -i '' 's/a/b/' f` |
| 절대경로 해석 | `readlink -f path` | `readlink`에 `-f` 없음 (`greadlink` 또는 `cd`+`pwd`) |
| 상대 날짜 | `date -d '1 day ago'` | `date -v-1d` |
| `base64` 줄바꿈 | 기본 wrap | `-b 0`으로 wrap 해제 |

그중 `sed -i`가 가장 악명 높다. 리눅스에서 잘 돌던 스크립트를 macOS에서 실행하면 `sed -i` 뒤에 오는 인자를 백업 확장자로 해석해, 엉뚱한 파일을 만들거나 에러를 낸다.

## 정리

이식의 핵심은 "같은 bash 스크립트니까 그대로 돌아가겠지"라는 생각을 버리는 것이다. 실제로 갈라지는 지점은 세 층이다. 서비스 매니저(systemd/launchd), 기본 유틸리티(GNU/BSD, `timeout` 유무), 자격 증명 저장소(파일/Keychain). 이 세 가지만 `command -v`와 분기로 감싸 두면 스크립트 하나로 리눅스와 macOS를 모두 지원할 수 있다.
